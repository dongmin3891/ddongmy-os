# 2026-11-09 Next.js 의존성 보안 감사

## 상태

- 대상: ddongmy Next.js 애플리케이션
- 배포 형태: Docker 기반 self-hosting, K3s, Traefik Ingress, 2 replicas
- Next.js 실행 형태: `output: 'standalone'`, 변경된 Dockerfile은 `node server.js` 실행
- Router: App Router
- 실행 환경: Node.js `v22.19.0`, npm `10.9.3`
- 상태: 같은 major의 보안 패치, Mermaid 12 major update, runtime artifact 최소화와
  로컬 회귀 검증 완료, 운영 배포는 수행하지 않음
- 결론: Next.js·React·sharp·Zod·Mermaid와 안전하게 갱신 가능한 transitive dependency의
  운영 취약점을 제거했다. `npm audit --omit=dev`는 0건이며, 전체 결과에 남은 개발 도구 경로의
  moderate 8건은 변경된 runtime artifact에 포함되지 않는다.

이 기록은 [의존성 보안 점검 Runbook](../dependency-audit-runbook.md)에 따라 작성했다.

## 점검 목적

SSR 성능 개선뿐 아니라 framework 취약점 대응, 장애 예방, 회귀 검증, 운영 rollback까지
설명할 수 있는 책임 범위를 실제 프로젝트에서 경험하는 것이 목적이다.

이번 점검에서는 다음 질문에 답했다.

1. manifest가 아니라 실제로 어떤 버전이 설치됐는가?
2. npm 보안 데이터베이스가 어떤 취약점을 보고하는가?
3. 공식 권고의 영향 범위에 현재 버전이 포함되는가?
4. ddongmy가 취약 기능이나 배포 조건을 실제로 사용하는가?
5. 안전한 패치 단위와 회귀 테스트 범위는 무엇인가?

### 배포 image와 `--omit=dev`의 차이

변경 전 Dockerfile은 dependency stage의 전체 `node_modules`를 runner stage로 복사해
TypeScript, ESLint, `tsx` 같은 개발 도구도 runtime image에 포함했다. 변경 후에는 Next.js의
`.next/standalone`과 `.next/static`, `public`만 runner로 복사하고 `node server.js`를 실행한다.

동일 이미지를 사용하는 트래픽 백필 Job이 `tsx`와 TypeScript 원본에 의존하고 있었으므로,
빌드 단계에서 해당 진입점을 단일 CommonJS artifact로 번들링해
`scripts/backfill-site-traffic.cjs`로 포함했다. Kubernetes Job도 이 artifact를 직접 실행한다.
따라서 웹 runtime과 백필 Job 모두 개발 의존성 없이 실행할 수 있다.

로컬 산출물 기준 전체 `node_modules`는 약 720MB, `.next/standalone`은 약 62MB였고 runtime
구성을 그대로 조립한 디렉터리는 약 65MB였다. standalone에는 `typescript`, `eslint`, `tsx`,
`esbuild`가 없음을 확인했다. 이는 Docker layer와 Alpine base image를 제외한 파일 크기이므로
최종 image 크기로 기록하지 않는다.

## 공식 권고와 프로젝트 영향 대조

### Next.js

변경 전 `next@16.3.4`는 여러 공식 권고의 영향 범위에 들어갔다.

| 권고 | 영향 범위 | 수정 버전 | ddongmy 사용 조건 | 판단 |
| --- | --- | --- | --- | --- |
| [Remote Code Execution in `next/og` ImageResponse](https://github.com/advisories/GHSA-vcvr-r3jv-pc5j) | `>=16.2.0 <16.3.6` | `16.3.6` | `ImageResponse`, `next/og` 사용 없음 | 노출 낮지만 영향 버전 |
| [RCE in Image Optimization API with SVG](https://github.com/advisories/GHSA-2464-fhr4-w9xw) | `>=16.0.0 <=16.4.0` | `16.4.1` | `next/image`, sharp, 원격 이미지 사용 | patch 우선순위 높음 |
| [DoS in App Router using Server Actions](https://github.com/advisories/GHSA-p3m5-59mp-jv5r) | `>=16.0.0 <=16.4.0` | `16.4.1` | App Router 사용, 명시적 `'use server'` 없음 | 영향 버전, 기능 노출 낮음 |
| `use cache` 및 cache 관련 후속 권고 | 권고별로 `16.3.4` 포함 | 최소 `16.3.8` 이상 | `'use cache'` 사용 없음 | 기능 노출 낮음 |
| [Cross-client response injection/disclosure](https://github.com/vercel/next.js/security/advisories/GHSA-pc58-hwjq-p385) | `>=16.0.0 <=16.4.4` | `16.4.5` | self-hosting과 reverse proxy 사용, upstream Response 직접 전달 패턴은 찾지 못함 | 최종 목표 `16.4.5` |

개별 권고의 가장 이른 수정 버전에서 멈추면 2026-11-03 후속 권고를 해결하지 못한다.
따라서 같은 major의 현재 stable patch인 `16.4.5`를 적용했다. 패치 후 npm audit에서
Next.js 관련 경고가 제거됐다.

### React Server Components

[React Server Functions DoS 권고](https://github.com/react/react/security/advisories/GHSA-h3gv-c5rc-p453)는
`react-server-dom-webpack`, `react-server-dom-turbopack`, `react-server-dom-parcel`의
`19.3.0`을 영향 버전으로 분류하고 `19.3.1`을 수정 버전으로 제시한다.

ddongmy는 App Router를 사용하고 Next.js 내부에 RSC bundle이 포함되어 있다. 별도
`react-server-dom-webpack` 설치가 없더라도 React와 React DOM을 `19.3.1`로 맞추고,
RSC 수정이 포함된 Next.js patch와 함께 검증했다.

### sharp

[sharp의 librsvg 취약점](https://github.com/advisories/GHSA-wq5f-xc86-pv6w)은 `0.35.5` 미만에
영향을 준다. ddongmy는 다음 두 경로에서 sharp와 이미지 처리를 실제 사용한다.

- Next.js Image Optimization
- Notion cover를 최대 1200px WebP로 변환하는 server code

`0.35.4`에서 `0.35.5`로 patch했다. 단순 설치 여부가 아니라 실제 runtime 처리 경로가
존재하므로 이미지 변환 단위 테스트와 production build를 함께 확인했다.

### Zod

[Zod memory exhaustion 권고](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5)는 `4.6.6`
미만에 영향을 준다. `4.6.2`에서 최신 patch `4.6.7`로 변경했다.

ddongmy는 외부 API, route body와 저장 데이터 검증에 Zod를 사용한다. 기존 body size 제한이
일부 DoS 위험을 낮추지만 영향 버전 자체는 교체한다.

### Mermaid와 DOMPurify

변경 전 `mermaid@11.17.2`는 `dompurify@3.4.15`를 가져왔다.
[DOMPurify SAFE_FOR_TEMPLATES bypass](https://github.com/advisories/GHSA-cg2g-xh64-v4q7)는
`3.4.4`부터 `3.4.16`까지 영향을 주며 `3.4.17`에서 수정됐다.

ddongmy는 Mermaid가 생성한 SVG를 `dangerouslySetInnerHTML`로 표시한다. Mermaid 설정의
`securityLevel: 'strict'`는 방어에 도움을 주지만 vulnerable sanitizer를 유지할 근거는
되지 않는다. framework patch와 분리해 `mermaid@12.3.0`으로 변경했고, 이에 따라
`dompurify@3.4.17`과 `katex@0.18.10`이 설치됐다.

[Mermaid 12.0.0 공식 릴리스](https://github.com/mermaid-js/mermaid/releases/tag/mermaid%4012.0.0)는
Node.js 22.12+, ES2024와 Safari 17.4+를 요구하고 기본 layout을 ELK로 변경한다. 현재 Node.js
22.19.0은 요구 조건을 충족한다. 기존 다이어그램 배치를 유지하기 위해 전역 설정에
`layout: 'dagre'`, `look: 'classic'`을 명시하고 기존 `theme: 'dark'`와
`securityLevel: 'strict'`는 유지했다. 정상 diagram, 잘못된 문법의 fallback과 외부 콘텐츠
입력을 실제 Chromium에서 회귀 테스트했다.

## 코드와 배포 조건 조사

| 확인 항목 | 결과 | 해석 |
| --- | --- | --- |
| App Router | 사용 | RSC·App Router 권고를 검토해야 함 |
| self-hosting | Docker + K3s + Traefik | managed provider 완화만 가정할 수 없음 |
| replicas | 2 | rolling update와 cross-client/cache 동작 확인 필요 |
| `next/image` | 사용 | local SVG는 `unoptimized`, 원격 Notion 이미지는 최적화 |
| `sharp` 직접 사용 | 사용 | Notion cover WebP 변환 runtime 경로 존재 |
| `ImageResponse`, `next/og` | 찾지 못함 | 해당 RCE의 직접 노출은 낮음 |
| `'use server'` | 찾지 못함 | 명시적 Server Action 노출은 낮음 |
| `'use cache'` | 찾지 못함 | cache 관련 일부 권고의 직접 노출은 낮음 |
| Mermaid HTML 삽입 | 사용 | DOMPurify transitive 취약점을 Mermaid 12로 해결하고 browser 검증 완료 |
| SVG 최적화 허용 설정 | `dangerouslyAllowSVG` 없음 | local SVG는 unoptimized, 기본 방어 유지 |

기능 노출이 낮은 취약점도 framework가 공식 영향 버전에 있으므로 패치를 생략하지 않는다.
이 조사는 긴급 완화 우선순위와 회귀 테스트 범위를 정하는 근거로 사용한다.

## 패치 결과

### 1차: 같은 major의 runtime 보안 patch

```bash
npm install --save-exact next@16.4.5 react@19.3.1 react-dom@19.3.1
npm install --save-dev --save-exact eslint-config-next@16.4.5
npm install sharp@^0.35.5 zod@^4.6.7
```

Next.js·React·React DOM은 호환 조합으로 함께 변경한다. `eslint-config-next`도 framework
버전과 맞췄다. Next.js·React·React DOM·eslint-config-next는 exact version으로 고정하고,
기존 정책에 따라 sharp와 Zod는 caret 범위를 유지했다.

### 2차: Mermaid major update

```bash
npm install --save-exact mermaid@12.3.0
```

Mermaid update는 생성 SVG, sanitizer, styling 변경을 쉽게 구분할 수 있도록 1차 patch와
별도 회귀 단위로 진행했다. Mermaid 12의 기본 layout·look 변경으로 기존 diagram이
불필요하게 달라지지 않도록 `dagre`와 `classic`을 명시했다.

### 3차: runtime image 최소화

```bash
npm install --save-dev --save-exact esbuild@0.28.2
npm run build:traffic-backfill
```

개발 의존성은 builder stage에서만 사용한다. runner stage에는 Next.js standalone artifact,
정적 자산과 번들된 백필 실행 파일만 복사한다. `ops/site-traffic-backfill/job.yaml`은 더 이상
`tsx`로 TypeScript 원본을 실행하지 않는다.

### 허용 범위 내 transitive patch

`source-map-js`, `postcss-selector-parser`, `brace-expansion`은 상위 패키지의 허용 범위 안에서
안전 버전으로 갱신했다. 남은 dev-only 경고를 해결하려고 `eslint-config-next`를 15 계열로
downgrade하거나 `npm audit fix --force`를 실행하지 않았다.

## 면접에서 설명할 수 있는 핵심

이번 경험의 핵심은 `npm audit` 실행 자체가 아니다.

> lockfile의 실제 설치 버전을 공식 보안 권고의 영향 범위와 대조하고, Next.js 내부 RSC
> bundle처럼 npm tree만으로 드러나지 않는 경로까지 확인했다. 이후 Image Optimization,
> Server Actions, `use cache`, self-hosting 등 실제 노출 조건으로 우선순위를 정했다.
> framework와 React의 호환 patch를 먼저 적용하고, major 변경이 필요한 Mermaid는 별도
> 회귀 단위로 분리해 실제 브라우저에서 SVG·fallback·외부 입력을 검증했다. 적용 후 clean
> install, 53개 테스트, 타입 검사, lint, production build와 로컬 smoke test를 수행했다.
> 운영 이미지는 Next.js output tracing을 적용해 개발 의존성을 제외하고, 같은 이미지를 쓰는
> 백필 Job은 빌드된 단일 artifact로 전환했다.
> 운영 배포 전 단계와 rolling update·관찰·rollback
> 단계를 구분해 실제로 확인하지 않은 상태를 완료로 기록하지 않았다.

이 설명은 성능 최적화뿐 아니라 공급망 보안, 장애 예방, 배포 안정성까지 책임질 수 있다는
근거로 사용할 수 있다.
